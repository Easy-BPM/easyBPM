# Epic 54 — Human-task SLAs, deadlines and escalations

Source: https://github.com/Easy-BPM/easyBPM/issues/54. Status: READY FOR IMPLEMENTATION. Requirements owner: Business Analyst. No application code changed in preparation of this specification.

## Context, evidence and journey

Confirmed current behavior: `Task` has PENDING/COMPLETED lifecycle, assignment, candidate users/groups, creation/completion timestamps and form reference, but no SLA fields. `TaskController` exposes paginated GET `/tasks`, GET/POST `/tasks/search`, task detail, claim, unclaim, draft, complete and privileged reassignment. Structured search filters are AND-combined. `TaskSearchSpecification` and `TaskService` restrict a non-admin to its assigned tasks or unassigned tasks satisfying BOTH candidate-user and candidate-group eligibility; empty candidate sets are permissive. This existing visibility rule remains authoritative.

Confirmed architectural boundaries: BPMN XML persists definitions; `BpmnXmlCodec` and modeler `utils/bpmnXml.ts` carry JSON node configuration in `easy:node` under `https://easybpm.local/bpmn/extensions`. `ProcessUserTaskHandler` creates tasks and timeline entries. `ProcessInstanceTimelineService`, `IncidentService`, `/incidents/{id}/retry`, and Micrometer-backed `MetricsService` are existing integration points. `/incidents/**` is protected by ACCESS_BPM_ADMIN. No partial SLA implementation was found in the inspected backend or frontend contracts; a controller example mentioning SLA escalation is documentation only. Frontends have flat root `App.tsx`, `types.ts`, `services` and `components` paths, not `src` directories.

Journey: a modeler author configures a deadline, optional advance alerts, and ordered overdue actions on a User Task, validates and deploys XML. Creation snapshots its SLA and deadline. A participant sees a countdown and status, finds urgent tasks, saves drafts and completes work without changing the clock. The engine records alerts and safely changes assignment/candidates when overdue. An operator inspects SLA aggregates, timeline and failed actions, corrects target data and retries a recoverable incident.

## Scope and decisions

In scope: all four applications; fixed and variable-derived durations; timezone configuration; persistent deadline/status/policy/actions; cluster-safe alerts/escalations; timeline/audit/incidents/retry; indexed search/counters; accessible live portal presentation; Admin dimensions and history; Prometheus instrumentation; tests and examples.

Out of scope: business-day/holiday calendars, country/union calendars, AI optimization, provider-specific email/SMS integrations, resetting deadlines by hand, escalation-driven process completion or node movement, redefining task visibility, new tenant model, arbitrary executable expressions, retroactive SLA assignment to existing tasks.

Proposed v1 business decisions, made concrete for development: use continuous elapsed time; P1D equals 24 hours, including DST transitions. Accept positive ISO-8601 Duration values with days/hours/minutes/seconds, reject calendar months/years and zero/negative SLA values. A configured server IANA timezone defaults to UTC; store all new SLA instants as UTC and return offset-qualified ISO timestamps, display with the configured zone. Zone affects presentation and is snapshotted, never changes elapsed-duration arithmetic. A dynamic expression is a single `${variableName}` reference to a process variable whose value is a nonblank duration or target string; resolve duration at creation and targets at action execution. No fallback from missing variables to literal names, no evaluation of code. Variable changes never recalculate a task deadline; target changes can repair a failed escalation.

AT_RISK begins at the earliest configured alert threshold. With no alerts, status changes directly from ON_TRACK to OVERDUE. No-SLA tasks expose null SLA fields/status and remain fully usable. SLA-enabled completed tasks have COMPLETED status regardless of whether completion was late; retain `completedWithinSla` to distinguish outcomes. At exactly dueDate an unfinished task is OVERDUE; completion at or before dueDate counts within SLA. Claim/unclaim/draft/reassignment/candidate changes never restart the clock.

Alerts have positive `beforeDue` offsets strictly less than the resolved SLA. Escalations have nonnegative `afterDue` offsets. Actions at the same instant execute in configured array order; stable IDs survive XML round trips. Each action runs at most once successfully per task/action ID. Candidate additions are set union and do not remove assignment; reassignment replaces assignee but preserves candidate sets. Existing visibility applies after changes, including intersection eligibility. A group target uses ADD_CANDIDATE_GROUP; REASSIGN always targets a user. All recipients are local username/group code identities already used by task APIs, never numeric user IDs.

Actions apply only to PENDING tasks in ACTIVE/WAITING instances. Completion/cancellation removes eligibility; FAILED instances defer actions until recovery without shifting deadline. Restart executes missed overdue escalations in schedule order. Missed alerts run only while still before dueDate; after dueDate they are durably marked skipped. Completion and escalation races serialize against the same authoritative task/instance state: if completion wins, no subsequent escalation may mutate it. Failed actions record an incident without completing a task, changing the deadline or advancing BPMN. Other configured actions may proceed; an action retry must never undo later successful assignment actions (stale reassignment retry conflicts).

## Functional requirements

FR-1. Modeler must edit fixed/expression SLA, zero or more advance alerts and zero or more escalation actions on User Tasks only, with node-specific errors and deploy blocking for static invalidity.
FR-2. Both XML directions and backend parser/deployment validation must preserve identical SLA configuration and stable action IDs. Imported definitions without SLA retain current behavior.
FR-3. Creation must persist the deadline, effective timezone and immutable policy snapshot, scheduling every configured action atomically with task creation. Runtime expression/offset errors follow existing process-engine incident handling; never silently create a supposedly SLA-enabled task without a deadline.
FR-4. Every task-query response, including mutation responses returning a task, must include authoritative nullable SLA fields. Status filters, counters and UI must agree at one captured query instant even if scheduler updates lag.
FR-5. Scheduler must durably record a logical alert event and a single successful escalation effect per task/action, recover after restart and handle concurrent replicas. Persist action results and timeline/audit facts atomically with database effects.
FR-6. Alert events must include stable event/action/task/instance IDs, dueDate, scheduled/executed timestamps and event type; durable internal publication is sufficient. External transport can redeliver with stable event ID; document consumer deduplication. In-memory publication alone does not satisfy durability.
FR-7. Support REASSIGN, ADD_CANDIDATE_USER and ADD_CANDIDATE_GROUP with literal/dynamic target; reject unsupported action/target combinations and blank/unresolvable/unknown/inactive local identities. No secret or arbitrary variable dump in events.
FR-8. Record configured/deadline, risk/overdue transition, alert, skipped action, successful/failed escalation and retry history with task/action correlation, actor, scheduled time and outcome. Record each transition once, including missed transitions recovered after restart.
FR-9. Expose paginated dueDate sorting and status/date-range filtering, counters and paginated history under the same visibility rules as task data; privileged aggregate dimensions are process definition, task node, assignee and candidate group.
FR-10. Portal must show due date, remaining/overdue time, text status and accessible non-color indication, support filtering/sorting, and refresh status without page reload while preserving selected task, form input and filters. Refresh at most 30 seconds after a boundary while visible; countdown updates may be local, authoritative status remains server-derived.
FR-11. Admin must provide SLA counters and grouped metrics, due-range/status filtering, task/instance history and recovery of failed escalation incidents using existing incident workflow.
FR-12. Retry is admin-only, correlated to the original failed action, rejects completed/cancelled/stale tasks or already successful actions, and marks the incident resolved only after success. Failed retry preserves recoverability and records a new attempt.

## API and BPMN contracts

Add node `config.sla` inside the existing `easy:node` JSON extension; do not invent a separate process-definition persistence format. Example:

```json
{"sla":{"duration":"PT4H","timeZone":"America/Sao_Paulo","alerts":[{"id":"warn-1","beforeDue":"PT30M"}],"escalations":[{"id":"escalate-1","afterDue":"PT0S","action":"REASSIGN","target":"${supervisor}"},{"id":"escalate-2","afterDue":"PT1H","action":"ADD_CANDIDATE_GROUP","target":"operations"}]}}
```

`duration` contains either a fixed duration or a single variable reference; `timeZone` is optional and overrides the server default for this task. `alerts`/`escalations` default empty. IDs must be unique across this task policy, nonblank and stable. Reject SLA on unsupported node types. Backend validates XML configuration independently of Modeler.

TaskResponseDto additive fields: `dueDate: string|null`, `slaStatus: ON_TRACK|AT_RISK|OVERDUE|COMPLETED|null`, `slaTimeZone: string|null`, `completedWithinSla: boolean|null`. Preserve existing `status: PENDING|COMPLETED` and timestamps untouched. For no-SLA or unfinished tasks completedWithinSla is null.

Extend POST `/tasks/search` existing filters with `field: "dueDate"` comparison operators and `field: "slaStatus"` EQUALS/NOT_EQUALS/IN/NOT_IN. `sort=dueDate,asc|desc` must use stable task-ID tie breaking and place null deadlines last. Due-range UI translates into GREATER_THAN_OR_EQUAL/LESS_THAN_OR_EQUAL timestamp filters; offsets required, inclusive boundaries. GET `/tasks/search` may add equivalent optional `slaStatus`, `dueDateFrom`, `dueDateTo` preserving existing assignee/status arguments. Invalid values/operators/ranges return 400, never silently drop a filter.

Proposed additive endpoints: POST `/tasks/sla/summary` accepts existing `{filters:[...]}` and returns `{onTrack,atRisk,overdue,completed,withoutSla,asOf,timeZone}` under task visibility; GET `/tasks/{id}/sla/events` returns paginated events `{id,taskId,actionId,eventType,scheduledAt,occurredAt,outcome,message,incidentId}` with privileged-only technical target details omitted for participants. GET `/admin/sla/metrics?groupBy=PROCESS|TASK|USER|GROUP&dueDateFrom=...&dueDateTo=...` returns bounded/paginated rows with dimension key/label and counters, total SLA-completed, completedWithinSla count/rate, successful/failed escalation counts and alert-to-completion sample count/average seconds. Percentage denominator excludes tasks without SLA, average uses the first successful alert per completed task and null when no samples. USER means current assignee (explicit UNASSIGNED bucket); GROUP means current candidate membership and a task can count in multiple group rows, document non-additivity. PROCESS means definition key; TASK means process-key plus node ID. Admin dates filter task deadlines.

Extend existing POST `/incidents/{id}/retry` dispatch for SLA escalation incidents, preserve worker incident behavior and existing request shape; authenticated actor takes precedence over supplied requestedBy. Response remains Incident. New stale SLA retry returns 409, invalid non-retryable incident retains current 400; missing incident 404. Additive endpoint paths can be adjusted for existing routing conventions only if the spec, services/types and tests change together.

## Persistence, permissions and errors

Append the next available Flyway version (current numeric latest observed V46); never alter applied migrations. Persist nullable new task SLA fields, immutable configuration snapshot, durable action schedule/outcomes/attempt correlation and unique successful logical action identity. Add indexes supporting unfinished due-date scans and dueDate/status searches. Existing rows stay no-SLA; no retroactive tasks/actions. Completed history retains all SLA evidence. New UTC fields must not reinterpret existing LocalDateTime task timestamps in a host-dependent timezone; derive creation instant explicitly and document the configured legacy interpretation if needed.

Task read/history/counters use current security authorities (ACCESS_PROCESS_PORTAL/TASKS_READ and task visibility; ACCESS_BPM_ADMIN sees permitted operational scope). Metrics/retry require ACCESS_BPM_ADMIN server-side. Native API client scopes must not bypass visibility or gain Admin privileges. Modeler deployment follows existing process write permissions. The repo has no confirmed tenant partition for this feature; preserve all existing isolation, introduce no cross-user aggregate leak. Automated effects act as system and audit that identity.

Static XML errors: deployment 400 with node/config path and actionable message. Invalid dynamic deadline: existing engine failure/incident path, no fabricated deadline. Invalid target: failed action and recoverable SLA incident, without partial candidate/assignment mutation. Search errors 400; unauthenticated 401; unauthorized 403; missing resources 404 on new endpoints; lifecycle/stale retry conflicts 409. Frontends preserve inputs and display retryable network/5xx failures. Repeated successful incident retry must not create a second effect. Overflow, invalid zone, unsupported units, duplicate IDs and oversized/invalid policy shape must be rejected consistently. No stack traces, tokens or secret values in user-facing messages.

## Non-functional requirements and architectural constraints

NFR-1. PostgreSQL is authoritative; transactional state changes preserve current instance/task locking order, idempotency and cluster concurrency guarantees. RabbitMQ carries notifications/work, never owns state advancement.
NFR-2. Scheduled actions survive restart and transaction rollback; successful effects and audit evidence cannot diverge. Test actual PostgreSQL contention/uniqueness, not only mocked invocations.
NFR-3. Default polling interval no greater than 30 seconds; bounded batches prevent starvation and unbounded memory loading. Query pagination/sort/filter and database indexes support operational datasets.
NFR-4. Dates include timezone offsets in contracts; UTC persists, configured IANA zone displays. Test DST, midnight and non-UTC servers.
NFR-5. Accessible labels and keyboard-operable filters; status conveyed through text and icons as well as color. No full reload/form loss for live refresh.
NFR-6. Prometheus exposes unfinished overdue gauge and alert/escalation success/failure counters; retry/skip/scheduler lag diagnostics are desirable. Avoid task IDs/usernames as metric labels. Logs use task/action/instance/incident correlation, outcomes and scheduled/executed times, without process variable payloads.
NFR-7. Backward compatibility: existing XML, APIs and no-SLA task lifecycle remain functional; new optional fields do not change existing status enumeration. Worker protocol remains unchanged unless an explicitly versioned internal event addition is necessary.
